# Daily Research Process

How the daily digest actually gets built. This is written so that any future run of this assistant — scheduled or manual — reproduces the same process.

## Why this isn't a standalone script

The obvious design would be a script that pulls each source's RSS feed on a cron job. That doesn't work here: this environment's shell has allowlisted network egress, and direct `curl`/`requests` calls to RSS/JSON endpoints (tested against CISA's KEV JSON, Krebs' feed, etc.) come back blocked. Fetching has to go through the assistant's own `WebFetch`/`WebSearch` tools instead of raw HTTP calls — and testing showed those tools handle HTML listing pages well (confirmed against krebsonsecurity.com, which returned full post text with dates and links) but not JSON or XML endpoints (the CISA KEV JSON URL returned empty content).

So the daily process is an agent run, not a cron script: each run, the assistant works through the catalog and fetches each source's human-readable page, not its raw feed.

## Steps

1. **Load the catalog.** Read `sources/catalog.md` for the full source list, and pull Tier 1 sources every run; pull Tier 2 sources every run as well unless they've been silent for several consecutive days (then check less frequently — use judgment, not a hard rule).

2. **Fetch each source.** Use `WebFetch` on the source's homepage/listing URL (recorded per-source in the category files under "Fetch method"). If a fetch returns empty or clearly JS-rendered content, fall back to `WebSearch` scoped to that domain (e.g., `site:cisa.gov known exploited vulnerabilities` with a recency term) rather than guessing at content.

   **If WebFetch is blocked network-wide** (the environment's egress allowlist rejects every source domain, not just one JS-rendered page), treat the run as an **incident, not a normal run**. The framework's grounding rule — every claim traces to a page actually fetched — cannot be satisfied by search alone, because search results are synthesized summaries, not pages. In this state: (a) put a prominent note at the very top of the digest saying the run was search-only and why; (b) treat every item as search-sourced under step 4's mandatory date-verification rule; (c) keep the digest deliberately minimal — high-confidence, date-confirmed items only — rather than producing a normal-looking digest from secondhand content; and (d) flag the environment problem itself in the run summary so it gets fixed rather than becoming the new normal. This mode is how a fabricated publish date got into the 2026-07-28 digest (a July 1 story written up as July 28 news), so the bar for inclusion is intentionally higher here.

   **Distinguish a per-site block from a network-wide one before declaring an incident.** A single source refusing to load is not incident mode. Two failures look similar in a run log but have opposite meanings and opposite fixes:

   - **Network-wide egress block** — every tracked domain fails with the same allowlist error, including domains known to work. This is the environment, and it triggers incident mode above.
   - **Per-site HTTP rejection** — the request reaches the site and the site refuses it, typically `HTTP 403 Forbidden`, while other domains fetch normally. This is that publisher blocking automated fetchers at their own edge. No allowlist change fixes it; the correct response is the per-source `WebSearch` fallback in this step, plus a note in the digest naming the source and the status code, and a line in the source's "Fetch method" entry so the next run doesn't rediscover it.

   As of 2026-07-31 the sources known to reject WebFetch this way are **cisa.gov** and **darkreading.com** (observed from a Claude Code session, not from Cowork — publisher edge blocks can vary by client and network, so re-confirm from the runtime that actually does the fetching before rewriting a fetch method). cisa.gov is the more consequential of the two, since CISA owns the KEV catalog and the ICS advisory stream — a run that treats a CISA 403 as an environment fault will wait for a fix that never comes, while the KEV additions it should be reporting go unread.

   **Fixing the environment (the actual fix):** the WebFetch tool executes inside Cowork's sandboxed VM, whose network egress is filtered against a per-user allowlist (Settings → Capabilities in the Claude desktop app; hostname-based, wildcards like `*.cisa.gov` supported). WebSearch is routed through Anthropic's backend and is *not* subject to that filter — which is why a blocked environment degrades silently to search instead of failing loudly. Allowlist changes only take effect in **new** sessions, not the currently-running one. For WebFetch to work as this process assumes, the allowlist needs the tracked sources' domains, currently: `krebsonsecurity.com`, `www.bleepingcomputer.com`, `thehackernews.com`, `www.darkreading.com`, `isc.sans.edu`, `defensivesecurity.org`, `rephonic.com`, `www.cisa.gov`, `nvd.nist.gov`, `www.cve.org`, `msrc.microsoft.com`, `osv.dev`, `blog.talosintelligence.com`, `unit42.paloaltonetworks.com`, `cloud.google.com`, `www.microsoft.com`, `www.securityweek.com`, `github.blog`, `github.com`, `openssf.org` (keep this list in sync with the category files when sources change).

   **Podcast/video sources are text-only in this framework.** We don't transcribe audio or watch video — we rely on written show notes/episode descriptions, which for a well-run news podcast already contain the substance (topic + link to the primary source per item). Raw podcast/YouTube RSS feeds return as unusable binary/XML through `WebFetch`, same as other XML feeds, and YouTube's own watch pages are JS-rendered and return empty — don't use either directly. Instead use whatever HTML mirror of the show notes actually renders (see Daily DefSec Brief's entry in `sources/news-analysis.md` for the current example: a third-party podcast tracker page, not the platform itself). If a source is added that has no such text mirror, note that explicitly rather than fabricating episode content from the title alone.

   **Prefer the official source over a third-party mirror whenever the official one actually renders.** Before settling on a third-party tracker/mirror as a source's fetch method, check whether the publisher's own site works through `WebFetch` — plenty of official pages are plain server-rendered HTML and work fine (e.g. `defensivesecurity.org`, a WordPress site, renders perfectly), while others are JS-rendered apps that return nothing (e.g. `defsecbrief.riverside.com`). Only fall back to a third party when the primary source genuinely doesn't render as text. When a mirror is used, say so explicitly in the source's catalog entry so it's clear the digest is one step removed from the publisher.

3. **Filter to the lookback window.** Default lookback is since the last successful daily run (roughly 24 hours; use 48–72 hours for the first run of a new week to catch anything missed over a weekend gap). Discard anything older even if it's still on the homepage.

   **Same-day re-run (a file for today's date already exists):** this happens when the task is manually triggered ("Run now") after the scheduled run already fired, or after the catalog/process itself was edited and someone wants to test the change same-day. Do not compute "the day after the most recent file's date" in this case — that produces a backwards or empty window. Instead: treat today's existing file as the starting point, use a short lookback (since that file was last written — check its content/mtime, or fall back to the last several hours) and **update it in place** rather than silently discarding it. Add a note under "Run Notes" at the bottom of the file (not the top — see step 7's formatting rules), e.g. "Updated intraday at [time] — re-run to pick up newly added sources" or whatever the actual reason is, so it's clear the file was regenerated rather than left stale. Preserve anything from the earlier version that's still accurate; don't drop items just because the file is being rewritten.

4. **Extract per item:** title, exact publish date, direct URL (the actual article/advisory permalink, not just the homepage), source name + tier, and a 2–3 sentence factual summary written from what was actually read — never inferred or filled in from the headline alone. Pull out CVE IDs, CVSS scores, and named threat actors/malware when present, since these are what make items scannable and searchable later.

   **Date verification for search-sourced items (mandatory).** WebFetch shows the publish date on the page itself; WebSearch does not — it returns a synthesized summary that frequently omits the date or phrases it relative to "now" ("published a week ago"). So the "exact publish date" requirement has a sharper form for anything that came through WebSearch rather than WebFetch: the date must be *positively confirmed*, not assumed. Before writing a search-sourced item into the digest, run a second, date-targeted query for it (e.g., `"<exact article title>" <site> date published`) and only include the item once a specific date is confirmed and falls inside the lookback window. If no date can be confirmed, the item doesn't go in — the same rule as any other unverifiable claim (step 9). Never default a dateless item to "today"; "it came back as a top result in this run" is a relevance signal, not a recency signal, and conflating the two is how a July 1 story got published as July 28 news in the 2026-07-28 digest.

   **A date used to reject an item needs the same proof as a date used to publish one.** Every rule above pushes in one direction: it guards against putting something in on a weak date. Nothing yet guards against *leaving something out* on a weak date, and that error is the more dangerous of the two, because it is invisible by construction — a wrongly included item leaves a wrong date on the page for someone to catch, while a wrongly excluded item leaves nothing at all. So: if a search-derived date is the *only* basis for dropping an otherwise in-scope item, run the same dedicated date-targeted query required for inclusion before dropping it. Do not write a confident exclusion rationale from a search summary's date.

   This is not hypothetical. The 2026-07-31 digest, as written by its incident-mode run, excluded JetBrains TeamCity [CVE-2026-63077](https://nvd.nist.gov/vuln/detail/CVE-2026-63077) — a critical unauthenticated RCE affecting all TeamCity On-Premises versions. Its "Date-verification exclusions" note under Run Notes states that "JetBrains' own advisory and BleepingComputer's coverage both trace to July 27, 2026," and its "Sources with no new items this run" entry drops the story as "outside this window even widened — so it was excluded rather than treated as new." The actual coverage was in window: [BleepingComputer's article](https://www.bleepingcomputer.com/news/security/jetbrains-warns-of-critical-teamcity-remote-code-execution-flaw/) is dated July 30, 2026 and [SecurityWeek's](https://www.securityweek.com/critical-code-execution-vulnerability-patched-in-teamcity/) July 31, 2026, both confirmed by fetching those pages directly from an environment where WebFetch worked. Both of those same entries also attach "CVSS 9.8" to the CVE; neither fetched article states a CVSS score for it, so that figure has no traceable source in the run's own material. The errors surfaced only when an independent re-run with working fetch re-checked the exclusions — nothing inside the file's own audit could have caught them, because step 9 walks only the items that made it in.

   **Incident mode makes this worse, not better.** Step 2's incident-mode instruction deliberately raises the bar for inclusion and tells the run to keep the digest minimal. That is the right instinct for guarding against false inclusion, but it applies active pressure toward dropping items at exactly the moment when the run's date evidence is weakest and least verifiable. A search-only run should therefore be *more* careful about exclusions, not less — the minimalism is meant to remove padding, not to remove real items that happen to be hard to date.

5. **Categorize** each item into one of:
   - Critical Vulnerabilities & Advisories (new CVEs, KEV additions, Patch Tuesday, actively-exploited flaws)
   - Active Threats & Incidents (breaches, ransomware, ongoing campaigns)
   - Threat Intelligence & Research (APT/malware analysis, TTP writeups)
   - Open Source & Supply Chain (OSS project vulnerabilities, dependency advisories, tooling)
   - Other Notable (anything credible that doesn't fit above but a security-focused reader would want to see)

6. **Flag high-priority items** — anything from a Tier 1 source involving: confirmed active exploitation, CVSS ≥ 9.0, a KEV catalog addition, or a major named incident (breach affecting a large population, critical infrastructure, or significant ransomware activity). These go in an "At a glance" section at the top of the digest.

7. **Write the digest** to `daily/YYYY-MM-DD.md` using `daily/TEMPLATE.md`. Every item must carry its source link — no unsourced claims. If a scheduled Tier 1 source couldn't be fetched this run, say so explicitly in the digest ("CISA advisories page unreachable this run") rather than silently omitting it.

   **Formatting rule — one metadata line per item:** keep the `**Source:** ... · **Published:** ...` metadata line to a single link and date. When an item covers multiple related dates/batches/links (e.g. several weeks of KEV additions under one heading), put the primary one in the metadata line and break the rest out as a bulleted list underneath — don't chain them together with semicolons in one line. Markdown renders a long single-line paragraph as one dense, hard-to-scan block regardless of how it's wrapped in the source file.

   **Formatting rule — CVE IDs are always links.** Every time a CVE ID appears anywhere in the digest (heading, "At a glance" bullet, `**CVE:**` metadata field, or body text), render it as a markdown link to the National Vulnerability Database entry: `[CVE-2026-16723](https://nvd.nist.gov/vuln/detail/CVE-2026-16723)`. This applies to every occurrence of the same ID, not just the first. Do this even when NVD doesn't yet have a populated entry for a brand-new CVE — the link is still useful once NVD catches up, and it's one canonical place to check CVSS/CPE details regardless of which source originally reported the flaw.

   **Formatting rule — Table of Contents.** Right after the title (before "At a glance"), include a `## Table of Contents` with a bulleted list linking to every `##`-level section that appears in that day's file, in the same order as the headings below it. Use GitHub's heading-slug convention: lowercase, spaces to hyphens, `&` dropped (leaving a double hyphen), e.g. `## Critical Vulnerabilities & Advisories` → `#critical-vulnerabilities--advisories`. Omit TOC entries for sections that don't appear that day (e.g. skip "Sources with no new items this run" if every source had something).

   **Formatting rule — run metadata goes at the bottom, not the top.** Anything about the mechanics of the run itself — lookback window, sources checked, outages, incident-mode notices, same-day re-run notes — goes in a `## Run Notes` section at the very end of the file, after "New source candidates logged today," not before "At a glance." Readers open this file for the news; the plumbing is reference material for when something looks off, not the first thing they should have to scroll past. See `daily/TEMPLATE.md` for the exact subsection layout (Lookback window and sources checked; Run notice, only when something went wrong).

8. **Log new source candidates.** If research surfaces a source not in the catalog that looks credible (see `METHODOLOGY.md` → "Discovering new sources"), add one line to `sources/candidates.md` with the URL and why it was flagged. Don't score or promote it in the same run — that's a separate, deliberate step.

9. **Final date audit before finishing.** After the digest is written, re-read every `**Published:** ...` line and confirm its provenance: the date either came verbatim off a fetched page, or was positively confirmed by a dedicated date-targeted search (step 4). Any item whose date can't be traced to one of those two moves out of the digest body into a short "Unverified this run" note (title + link only, no summary). This is a structural check, not a judgment call — prose rules earlier in this document were skimmed past once already; this step exists so the last thing a run does is catch that.

   **Audit the exclusions too.** Re-reading `**Published:**` lines only walks the items that made it in, so by construction this audit cannot see a wrongly dropped item. Close that gap: for any item considered and then rejected on date grounds, record it under `## Run Notes` as a one-line entry with title, link, the date you concluded, and how that date was established (fetched page, dedicated query, or search summary only). Anything resting on a search summary alone is not yet excluded — go verify it or include it.

   Two things follow from writing exclusions down. A reviewer gets something to check, which is the whole point. And a run that has to name its evidence in public tends to notice when it doesn't have any — the 2026-07-31 TeamCity exclusion was written out in full prose and still went unchallenged, but it was written as a conclusion rather than as a claim with its provenance attached.

10. **Never fabricate.** If nothing new came from a source, say "no new items" rather than padding the digest. If a claim can't be traced to a specific fetched page, it doesn't go in the digest. This applies to URLs too: always copy a link verbatim from the page or search result you actually retrieved. Never hand-construct or shorten a URL from memory (e.g. guessing the path structure from other similar URLs seen in the same batch) — a plausible-looking URL that wasn't copied directly is exactly the kind of thing that quietly 404s.

## Scheduling

This process runs as a scheduled task (see `mcp__scheduled-tasks__create_scheduled_task`) rather than a shell cron job, since it depends on the assistant's own fetch tools. The task prompt should point at this file and `sources/catalog.md` directly so behavior stays in sync with any future edits to either.
